# Structure overview

All content on this site is scatered in directory `pages`.
Generally all the html files in it represent diffent page covering some kind of subject.

Direct children directories in that `pages` directory represent theme/subject categoriess.
So when I ask you to create new html page usually try to find relevent directory and extend from there.
Many times given page could be just html like example in https://github.com/stopsopa/stopsopa.github.io/blob/master/README.md#template
which in this repository is code block from README.md under section 'TEMPLATE'. There is also minimalistic version in code block under header 'template minimal'

Anyway, when I ask you to create page use these templates to create it. Center piece for given requested page will be index.html create from these templates.
We have to usually figure out to what category to put that html file use for that file pages/PAGES.md, this file is autogenerated and contains brief description of mostly all what is in 'pages' directory.
Based on these find best place for that.

Knowing what I will tell you what I'm creating this page for

find best directory.
When directory will require creating some assisting files. put that html file in it's own directory in the directory you determine reding pages/PAGES.md.

When I mention that that script is a "service" then find the place for it somewhere in pages/services (this is special folder with more 'functional' pages in this project).

in order to figure out how to work with services read (read only when you will be asked to crate a 'service') pages/services/SERVICES_RULES.md file how to structure. When I won't mention how to configure that service then ask me interactively what style of service I will need. Styles fall into categoreis mentioned in pages/services/SERVICES_RULES.md.

once file is create we have to find place to link that html file entrypoint to general navigation with linkg among other pages in 'pages' directory. Usually you will link it somewhere in index.html in parent directory from where you've decided to place the html file, unless instructed otherwise.

If you determine that that index.html will be placed in pages/[my_new_section]/index.html becasue it doesn't fall into any preexisting category mentioned in pages/PAGES.md then we have to link it as main section in top list in index.html which sits in the main directory of this project.

If you've determined that I'm asking about service then link it into "services" section in the file index.html which sits in the main directory of this project.

When linking something to Services section of index.html which sits in the main directory of this project always add emoji icon matching the service purpose on the left side of the link (only in Services section, other sections have no icons).
Every link there has one. Add it as `data-icon` attribute of the `<li>`, not as text:

```html
<li data-icon="🔌"><a href="pages/portsregistry/portsregistry.html">Ports Registry</a></li>
```

It is rendered by css `li[data-icon]::before` defined in `<style>` of that index.html. Reason: the list has `data-do-sort` which sorts by text of `<li>` - emoji typed as text would break alphabetical order.

# When taking template content

You might also ask what sections from template to take, there are few:

- for most new pages script tag with `var p = new Promise(function (res) {` is not needed, so by default don't add it to new index.html unless I answer that I need it - but generally ask if I will need it. The section purpose is to change all domain.com to our custom domain before hydrating rest of the javascript on the page.
- ask also if we will need script with `typeof window.allLoaded` - by default it is normally not needed
- also ask if we need `<h1>Table of Contents</h1>` see section "manual TOC" of the README.md, normally TOC is needed but ask for it and if I say I don't need TOC then don't add toc to body element and don't create .cards.toc at all

rest of the template have to be taken as is - especially loading /js/github.js

# Storing data: pages/useCustomState.ts

Default library for storing data of a page/service (per user, survives reload, shared between devices).
It is a general interface for storing tree like structure. Firebase under the hood is just transport protocol and
storage source - never call anything firebase specific from a page, the interface provides what it provides.
Don't import pages/databases/firebase/useFirebase.ts directly.

Needs React and imports, so `*.entry.tsx` (mode "imports" from pages/services/SERVICES_RULES.md). In html before the bundle of the page:

```html
<script src="/public/preprocessed.js?my_page"></script>
<script type="module" src="/dist/firebase.core.entry.bundle.js"></script>
<script type="module" src="/dist/my_page.entry.bundle.js"></script>
```

```tsx
import useCustomState from "../../useCustomState";

interface Todo {
  text: string;
  done: boolean;
}

// type of the whole tree stored in the section - whole page/service has to follow/use this type
interface MyState {
  todos?: Record<string, Todo>;
}

const { ready, error, username, userId, get, set, push, del, signIn, signOut } = useCustomState<MyState>({
  section: "my_namespace", // root of the tree, own (unique) for each page/service
});

useEffect(() => {
  if (ready) {
    loadData();
  }
}, [ready]);

// shared screen for "signing in / signed out / error" with "Sign in" button - always use it, don't dump json of the error
// import CustomStateGate from "../../CustomStateGate";
if (error || !ready) return <CustomStateGate ready={ready} error={error} signIn={signIn} />;
```

Rules:

- `section` - each page/service uses own unique one (check that it is not used already: search for `section` next to `useCustomState` in pages/).
- Always define type of stored data and pass it as `useCustomState<MyState>` - then `get` / `set` / `push` are typed by the key. Use these types across the whole page.
- Authentication happens behind the scene. Page only waits for `ready: true` before touching data and rendering final UI. `signOut()` -> `ready: false`, `signIn()` -> back.
- Keys are relative to the section: `"todos/abc"` or `["todos", "abc"]`, no key = whole section.
  `get(key)` (null when empty), `set({ key, data })` overwrites, `push({ key, data })` adds child and returns its generated key, `del(key)`.
- `username` - human readable, `userId` - stable unique id.
- Rest (shape of the data, when to load/save) is up to particular page.
